# M12 reuse audit: adding 7 Wonders second edition

Superseded in part: for the room and slice plan, read [platform-architecture.md](platform-architecture.md), not Question 2 below.

## One-page summary

@OpenAI. Read-only source audit of master `a063cee`, 2026-10-21. Scope: the same site and Go binary, a separate 3 to 7 player game, mixed human and bot seats, and a lazy client route. No builds, tests, browsers or extra agents were run. File references identify the inspected revision. Estimates describe refactoring scope, not elapsed time: small means a local seam, medium crosses one subsystem, large changes a lifecycle or contract. Risk means potential regression to existing Duel behavior. Proposed checks below have not been run.

The project has good reusable infrastructure, but it does not yet have a reusable game host. The room actor, store, wire state and client session all depend directly on Duel state. Keep the Duel engine and catalog intact; introduce adapters around them. Reuse identity, sockets, atomic file operations, resource guards, shell controls and low-level presentation machinery. Build the new rules, observation model, hand UI and simultaneous resolution separately.

The five largest risks are:

- **Independent picks versus one version.** `room.act` accepts only `base == r.version`, and every accepted action increments that version (`server/internal/room/room.go:513`, `server/internal/room/room.go:619`). Two players choosing from one round snapshot cannot both succeed unchanged. A decision token must identify the round and seat independently of transport updates. Keep Duel's exact-base rule behind its adapter.
- **Private submissions and durable replay.** Current history records one `ToMove` action; action strings normally omit the actor (`server/internal/room/game.go:44`, `server/internal/store/file.go:118`). Haftgane must durably identify each submitting seat, restore accepted private picks, resolve a round deterministically, and hide unrevealed keys from events, history and spectators. Widening `choices` or seat arrays does not accomplish this.
- **Stored-room compatibility.** Store load/save, exported logs and candidate preflight all call the one Duel engine, with one `RulesVersion` (`server/internal/store/replay.go:114`, `server/internal/store/check.go:35`). Dispatch by game before replay. Preserve D28 and D29, legacy Duel rooms, archive behavior, unknown fields and deployment refusal semantics.
- **Several bots in mixed rooms.** Scheduling is enabled only for `ModeAI`, has one task, targets `ToMove`, and discards results when the global version changes (`server/internal/room/bot.go:42`, `server/internal/room/bot.go:130`). Use per-seat, per-decision task generations and the existing global fair permit pool. Six bots must not gain six independent CPU entitlements.
- **Shared client imports and information tests.** Root tooltips import Duel card rendering, English tables are eager, and the service worker precaches every build chunk (`web/src/lib/components/shell/TooltipStack.svelte:7`, `web/src/lib/i18n/index.ts:17`, `web/src/service-worker.ts:76`). The frame leak checker is specifically about Duel structures and the Great Library, not hands (`e2e/fixtures/leak-check.ts:1`). Separate renderers and game catalogs, and add an independent hand-visibility oracle.

Recommended coexistence: globally unique existing room codes, a stable game discriminator such as `duel` or `haftgane`, game-scoped rules versions/catalogs/scenarios, and a discriminated state payload. Keep `/play/<code>` working as a lightweight room entry that loads the right renderer after server metadata. Separate typed engine packages and generated outputs prevent collisions between similar card names. A generic metadata lookup would be new work: the actual HTTP router exposes `/api/rooms/{code}/log`, not `/api/rooms/{code}` (`server/internal/httpapi/httpapi.go:82`).

Generalize in measured slices, with only Duel registered first. Start with compatibility dispatch and extracted resource primitives, then typed envelopes and runtime adapters, then seat/lifecycle policy, bot scheduling, session policy, and client import boundaries. Keep each slice behavior-preserving for Duel. Do not invent a universal rules engine, a shared payment calculator, or a seven-player variant of Duel's board. New decisions are needed for simultaneous commitment, payment choices, mixed-seat lobby/start rules, disconnect/resignation, undo boundaries, per-game compatibility and download budgets.

## Per-module findings

### Server engine and catalog

**Duel-only: `server/internal/engine` and `server/internal/engine/catalog`.** New rules and catalog belong in a separate package. Size large if generalized in place; Duel risk high. Copy architectural patterns and test techniques, not the current game model.

- `server/internal/engine/state.go:19` defines a two-value `Seat`; `server/internal/engine/state.go:22` implements `Opp()` by XOR. `server/internal/engine/state.go:261` has one `ToMove`, and `server/internal/engine/state.go:269` stores `[2]Player`. `server/internal/engine/state.go:237` has one winner or shared victory and `server/internal/engine/state.go:238` has two scores. `server/internal/engine/state.go:285` is a single conflict pawn, not neighbor military comparisons.
- `server/internal/engine/legal.go:58` derives legal actions from `s.ToMove`. `server/internal/engine/action.go:102` has a Duel action union; ordinary construct/discard/wonder keys identify a card without identifying the actor (`server/internal/engine/action.go:191`). New hand cards may require separate card-definition and physical-copy identities; verify this against the inventory rather than treating one slug as one instance.
- Setup/dealing/RNG, draft, structure/accessibility, affordability/payment, city/effects/hooks, science, military, wonders/pending, age transition, scoring and resign are all Duel rules. The similarly named Haftgane resources, chains and colors do not make their implementations portable.
- `server/internal/engine/catalog/types.go:24` fixes 73 cards, 12 wonders and 10 tokens. `server/internal/engine/catalog/types.go:92` is a set of card-definition ids, which cannot represent repeated instances. This `[2]uint64` is a bitset capacity, not a seat pair. Do not mechanically replace every `[2]` in the repository.
- `server/internal/engine/catalog/types.go:440` models five resource counts; its canonical resource notation is stated at `server/internal/engine/catalog/types.go:457`. `server/internal/engine/catalog/types.go:484` has only self and maximum-city counting scopes. `server/internal/engine/catalog/types.go:599` gives a card one chain input/output and `server/internal/engine/catalog/types.go:617` gives a wonder one cost/effect list. Haftgane's board sides/stages, neighbor effects, production, chains and resource inventory need fresh types and verified data.
- Keep `catalog/{cards_age1,cards_age2,cards_age3,guilds,wonders,tokens}.go`, registry, compiled lookup, DSL, verification CSVs and golden data scoped to Duel. Similar artwork can be mapped separately without sharing rule definitions or numeric ids.
- Observation/determinization are Duel-only: `server/internal/engine/observe.go:86` hides the shared structure and library offer; `server/internal/engine/observe.go:255` combines two players' tokens. Haftgane observation must include the viewer's hand and any information legitimately learned through passed hands, while excluding other players' pending choices. Its bot cannot receive the real room state.
- View building/event filtering/hints/review facts are also game-specific: `server/internal/engine/view.go:56` makes only `ToMove` a decider; `server/internal/engine/view.go:176` computes two costs per visible slot. Haftgane needs its own whitelist builder and private-history policy.
- Replay/hash/scenario mechanisms are useful examples, not a common state serializer. `server/internal/engine/replay.go:95` validates logged seats against `ToMove`; `server/internal/engine/replay.go:137` hashes the fixed Duel representation. Keep Duel hashes stable while adding an independently versioned Haftgane replay format or tagged log payload.
- Deterministic setup, integer arithmetic, array-based state, pure cloning, generated canonical keys, membership validation, public-only AI observations and redaction tests remain useful constraints. Small utility extraction can wait until both engines actually need it. In particular, changing integer ids, registry order, RNG consumption or action parsing while extracting common code risks a D28 semantic compatibility change even when old keys still parse.

### The engine boundary required by the room

**Generalizable: room-to-engine adapter. Size large; Duel risk high.** Today there is no engine interface. `server/internal/room/config.go:51` returns `engine.State` from storage and `server/internal/room/config.go:61` defines bots over `engine.Observation` and `engine.Action`. `server/internal/room/room.go:56` embeds state. `server/internal/room/game.go:18` constructs scenarios/games, `server/internal/room/game.go:101` enumerates canonical legal actions, `server/internal/room/room.go:610` applies actions, `server/internal/room/frames.go:43` builds views/hints/events, and `server/internal/room/room.go:825` hashes state. Undo/rematch/review/tutorial inspect further internals.

A minimal conceptual interface, implemented outside the pure rules package, is:

```go
// Sketch only. Named payloads are validated tagged unions, not arbitrary JSON.
type Runtime interface {
    Descriptor() Descriptor // game id, rules/catalog versions, bounds/capabilities
    Status() GameStatus
    Decisions(viewer Viewer) []Decision // seat, stable decision token, readiness
    Submit(seat SeatID, token DecisionToken, key string) (Transition, error)
    Snapshot(viewer Viewer, hints GameHints) GameView
    FilterHistory(viewer Viewer, entries []RecordedAction) []HistoryEntry
    Hash() string
    Result() GameResult
    CheckpointForUndo(seat SeatID) (Checkpoint, bool)
}

type Factory interface {
    New(setup GameSetup) (Runtime, error)
    Restore(setup GameSetup, actions []RecordedAction) (Runtime, error)
}
```

`Submit` must select the engine's own action from that seat's legal set, validate the decision token, and return actor-explicit durable records plus filtered-transition inputs. The adapter must not manufacture an action from unchecked client fields. `New`/`Restore` validate game-scoped options, seat count and scenario. Descriptors provide seat/action/key/file bounds and log-download policy. Whitelist snapshots and filtered histories are separate operations because a previously private choice can become public only at resolution.

A `Transition` needs to distinguish private pick acceptance, public round resolution, termination and any additional decision phases. A transport revision is monotonic; a decision token can remain valid while unrelated seats submit. Retrying one seat's accepted pick must never submit twice, including after the 32-client seq LRU forgets the client. The current old-base fallback is insufficient once independent requests may share a base (`docs/protocol.md:870`). Decide whether accepted choices are immutable or replaceable; replacements require their own revision rules and durable records.

Keep scheduling, clocks, identity, network membership, seq dedup and atomic persistence outside the rules. Keep public legality/payment, simultaneous resolution, neighbor relationships, phase progression and hidden-hand knowledge inside the game implementation. Bot observation and optional hint/review/tutorial providers can be separate adapter capabilities; do not require every game to implement Duel's advisor. Rematch needs validated setup cloning, not inspection of engine options.

Tradeoff: one large interface would move too much Duel behavior into generic code. Introduce a Duel facade first, retain typed Duel state behind it, and extract only proven common host operations. A separate Haftgane coordinator using shared infrastructure is safer than contorting Duel turn scheduling to emulate simultaneous play; the architect can choose whether the coordinators eventually share one actor implementation.

### Room actor, manager and lifecycle

**Generalizable: `server/internal/room` as host infrastructure, with substantial Duel policy extracted. Size large; Duel risk high.**

- **Actor and capacity.** `server/internal/room/room.go:169` serializes inbox messages, while manager reserve/eviction/idle bookkeeping (`server/internal/room/manager.go:346`, `server/internal/room/room.go:832`) is game-independent. Reuse actor ownership, context cancellation and idle eviction; ensure a seven-seat room's state, history and active jobs fit the configured memory budget. An actor serializes submissions without making game choices sequential in the rules.
- **Creation/seats/modes.** `server/internal/room/manager.go:138` randomly picks only one bit; `server/internal/room/manager.go:169` assigns the other seat with `1-seat`. `Spec.Seats` is `[2]store.Seat` at `server/internal/room/manager.go:195`. `checkSeats` bans bots online, requires exactly one bot in ai, and recognizes a same-user pair as hot-seat (`server/internal/room/manager.go:300`). Use a game descriptor for seat bounds and a roster for each seat's controller. Keep game type, online/local access policy and bot roster distinct.
- **Admission/lobby/start.** `server/internal/room/room.go:344` treats exactly two held seats as hot-seat, online auto-claims the first opening, and hot-seat claims 0 and 1 (`server/internal/room/room.go:355`). `status()` becomes playing as soon as there are no open seats (`server/internal/room/room.go:792`). Haftgane needs an explicit roster freeze/start policy, bot filling/replacement policy, and permissions for seat selection or configuration. Do not auto-start merely because the host selected bots for empty positions.
- **Membership and claims.** `member` stores one `engine.Seat` plus special roles (`server/internal/room/room.go:30`); `closedTo` accepts a two-seat array (`server/internal/room/room.go:381`). Generalize human membership/seat ownership and leave the Duel hot-seat role adapter intact. Pending hand views must never be exposed to someone who only owns a different seat.
- **Dedup.** `lru.go` and `(effective user, clientId)` keys at `server/internal/room/room.go:577` are reusable, with current bounded memory and stored high-water seqs. Keep duplicate acknowledgement before permission/turn checks (`server/internal/room/room.go:492`). Accepted private picks need persistent seat/decision identity as well as client seqs; a changed global version must neither cancel another seat's legitimate choice nor permit a forgotten duplicate to take effect again.
- **Versions and legality.** `server/internal/room/room.go:581` authorizes only `state.ToMove`; `server/internal/room/room.go:513` requires the exact global base. Replace the policy with engine-specific decision validation, while preserving Duel's existing rule. Snapshot revision, round identity, submission state and resolve point must be distinct and documented. Never auto-retry a stale Haftgane key against a different hand.
- **Commit and persistence.** `server/internal/room/room.go:607` applies one action, appends one key/history record, increments version, saves, starts the next bot and broadcasts. Haftgane needs accepted private submissions persisted before acknowledging the durability it promises, plus deterministic all-picks resolution. Current save failure keeps playing in memory and marks the room dirty (`server/internal/room/room.go:802`); explicitly settle whether that same durability contract is acceptable for locked simultaneous picks.
- **Bots.** `server/internal/room/bot.go:25` has one task; `server/internal/room/bot.go:43` requires ai mode; `server/internal/room/bot.go:46` uses `ToMove`; `server/internal/room/bot.go:131` validates against the current room version. Schedule eligible bot seats in online rooms too. Freeze each observation at the decision boundary, use seat/round/generation tokens, cancel only invalidated tasks, and derive deterministic seeds with seat and decision identity (`server/internal/room/bot.go:35` currently mixes only room seed and ply).
- **Undo.** `server/internal/room/room.go:635` bans online undo; `server/internal/room/room.go:691` cuts at the last human action and discards all later bot replies. This is Duel policy. A Haftgane bot room must decide whether undo retracts an unexposed pick or restores a whole round before all bot choices; later revealed/passed hands cannot safely be treated as one last-human ply. Keep disabled/online/spectator reasons server-owned.
- **Resign.** `server/internal/room/room.go:525` expects a terminal `resign:<seat>` and immediately ends the game with an opponent victory in the engine. Haftgane needs a new outcome policy: replacement bot, abandoned seat, whole-room cancellation or continued ranking. This cannot be generalized by choosing one of six opponents as winner.
- **Rematch.** `server/internal/room/room.go:738` lets a seated player create one persistent rematch, copies options and seats, resets link epochs and keeps admin/hints/undo. The one-new-room/idempotent behavior is useful. Preserve game type and roster; decide consent, lobby re-entry and whether absent humans become open slots or bots. Retain tutorial-to-normal-Duel behavior separately.
- **Hints/admin.** `server/internal/room/hints.go:92` and `wire/hints.go` provide reusable admin checks, seq dedup, bounded room log and shared settings. Hint families, defaults and advisor strengths are Duel-only. `server/internal/room/frames.go:47` computes one shared hint object; Haftgane may require public facts plus seat-private hand facts. Never compute hidden-hand advice in one shared object then broadcast it to all viewers.
- **Review/tutorial.** `server/internal/room/review.go:200` has two review slots and deep Duel AI/turn-boundary assumptions (`server/internal/room/review.go:342`). `tutorial.go` and `server/internal/tutorial` derive a fixed Duel script. Leave both Duel-only providers. They should be optional runtime capabilities, not prerequisites for Haftgane.
- **Views/history/spectators.** `server/internal/room/frames.go:25` has three viewer cache entries, two players plus spectator. `server/internal/room/frames.go:64` gives hot-seat the current decider's view, `server/internal/room/frames.go:154` has two presence booleans, and `server/internal/room/frames.go:223` derives `canAct` from one `ToMove`. Use seat-count-sized caches and a separate spectator projection. Preserve per-viewer event/history filtering, including reconnect and undo. Public ready flags do not imply public card identity.
- **Presence/names/limits.** `server/internal/room/identity.go:202` numbers names through a two-seat array; `server/internal/room/identity.go:22` scans two seats for claims. Reuse stable collision numbering and connection-based presence over a roster. Admission currently reserves capacity per seated user, so the documented maximum is three times the per-user limit (`server/internal/room/room.go:320`); seven humans change that bound. Recalculate connection/inbox/frame memory limits without preventing a reconnecting player from reclaiming their seat.
- **Outbox.** `outbox.go` is generalizable, medium size and medium risk: bounded queue, latest snapshot and ack preservation are useful. Its event concatenation and `continues` test depend on Duel `View.Ply` (`server/internal/room/outbox.go:95`, `server/internal/room/outbox.go:139`). A private submission may advance transport revision without a public move; merged resolution events need explicit round/history identity and redaction before enqueue. Preserve accepted-pick acknowledgements under coalescing.
- **Small reusable files.** `clock.go`, client metadata/lifetime plumbing, error plumbing and seq LRU mechanics are game-agnostic; exported signatures involving current wire types need the envelope change. Do not rewrite these merely because they live beside Duel-specific policy.

### Store, exported logs and compatibility

**Generalizable: `server/internal/store`. Size large overall; Duel risk high.** Atomic IO, code generation, locking, archive movement and retention algorithms are reusable; replay, room schema and log export are not yet engine-neutral.

- `server/internal/store/file.go:14` fixes file schema 1. `server/internal/store/file.go:107` stores two seats and concrete `engine.Options`; `server/internal/store/file.go:144` stores `*engine.Result`; `server/internal/store/file.go:159` stores Duel hints. Add a tagged setup/options/result/hints payload and an actual seat count. File schema, game id, game rules version, wire protocol and catalog hash have different jobs; keep them distinct.
- `File.Actions` currently contains only strings. The replay state tells the actor for each key. Haftgane persistence must supply seat identity or use canonical seat-qualified keys, and record all pending picks or an equivalent reconstructible commitment state. Document which records are private until resolution and how partial rounds survive restart.
- `server/internal/store/store.go:78` replays before Save and computes the Duel hash at `server/internal/store/store.go:97`. Load returns `engine.State` (`server/internal/store/store.go:118`). `server/internal/store/replay.go:27` constructs Duel scenarios and `server/internal/store/replay.go:114` compares one global `engine.RulesVersion`. Move replay/assessment behind a per-game registry and keep the IO layer ignorant of rules state.
- **D28 remains binding.** Legal same-game/same-rules replay is canonical; hash-only refresh preserves activity time, identity, settings and unknown additive fields. `server/internal/store/io.go:64` patches raw JSON fields for that reason. Rules mismatch or failed replay archives durably; unknown schemas are untouched. An unknown game is an unsupported format/engine, not permission to archive it as a broken Duel replay.
- A missing game field must have an explicit legacy-Duel interpretation. Adding an optional discriminator may fit an additive schema evolution, but changing seat/options/result encoding may require a new schema. Either dual-read or migrate explicitly. An old binary will not necessarily tolerate a Haftgane room merely because it can decode schema 1; rollback preflight must refuse unsupported live rooms.
- **D29 remains binding.** `archive.go` moves without overwriting and synchronizes per code. `server/internal/store/reaper.go:42` retains bounded archives with existing 30-day/1000-file/64-MiB policy. Share these across games, plus live 7/14-day retention, and count both games against the same archive resource budget. Unsupported or malformed files must not be deleted by a permissive new reaper.
- `server/internal/store/io.go:37` derives a 704-KiB read cap from max keys/history, room-log entries and header allowances. Recalculate against seven seats, game options, commitments, seq records and result size; do not blindly raise it. Re-evaluate history entry/event caps and actual generated worst cases together. Keep a bounded initial read before trusting a discriminator.
- `server/internal/store/code.go:12` uses six-character opaque codes. `server/internal/store/store.go:199` and archive existence checks can allocate for both games unchanged if all games share the code namespace. A code need not encode its game.
- `server/internal/store/log.go:18` returns `engine.Log`; `server/internal/store/log.go:34` and `server/internal/engine/replay.go:30` use `ajayeb-log/1`. Generalize download dispatch without weakening strict final-hash verification. Completed-game export can contain seeds; running-game export must not. `server/internal/httpapi/gamelog.go:120` currently reads Duel `HideAtEnd`, so expose a game-specific download/reveal capability rather than inspecting foreign options.
- `server/internal/store/check.go:15` contains one integer `rules`, and `server/internal/store/check.go:101` assesses every file through Duel. Add per-game capabilities/rules and counts while retaining trustworthy aggregate refusal counts. Unsupported games are operational/schema support errors, not silently skipped rooms.

### Identity, WebSocket and HTTP

### AI and commands

**Duel-only: most of `server/internal/ai`.** `bot.go`, random/greedy, evaluation/weights, rollout, ISMCTS, rank/review, arena storage, parallel search, level calibration and paired tournaments use Duel actions/observation/two-player utility. Haftgane requires its own legal-move evaluator, hidden-hand model, selection policy and performance/strength evidence. Neither zero-sum assumptions nor paired-seat win rates transfer automatically.

**Game-agnostic permit core, generalizable wrappers: `ai/pool.go`. Size small to medium; Duel risk medium.** `AcquireFor`/`ReleaseFor` use context and string keys only. Extract these without changing fairness. The pool selects fewest-held slots, then longest-since-grant key, FIFO within a key (`server/internal/ai/pool.go:18`, `server/internal/ai/pool.go:178`, `server/internal/ai/pool.go:187`); default per-key cap is 2 and runtime-based pool default at least 1 (`server/internal/ai/pool.go:51`). ## Question 1: how the two games coexist

Use an explicit **game identity** independent of mode and version. The names below are proposals, not existing API fields.

1. Keep a single room-code namespace and existing six-character validation/allocation. Put `game` on room setup, API/ws create requests, created/room metadata and state discriminator. Omitted `game` means legacy Duel only where explicitly documented. Unknown values fail validation. Join by code discovers game from the stored header, never trusts a caller-selected engine, and preserves both current `/play/<code>` invites and device-link fragments.
2. Keep mode/access separate from the roster. A `haftgane` online room can contain both humans and bots; `ModeAI` must no longer be the only signal that bots exist. New setup carries seat count and typed per-seat controller configuration. Lobby/start/fill/replace operations need explicit admin validation and a frozen setup once dealing begins.
3. Persist game identity before replay dispatch, with rules versions per game and game-scoped options/scenario/result/hints. Preserve legacy Duel schema/read behavior and D28/D29. A deterministic log includes actor-explicit private submissions and deterministic resolution order, or canonical seat-qualified keys with equivalent information. Never serialize accepted picks only in an unpersisted room map. Keep the seed out of live client payloads.
4. Prefer `/play/<code>` as a lightweight generic room entry that joins/loads public metadata then dynamically imports the game's module. This keeps old URLs and `isGamePath` simple, at the cost of an extra asynchronous renderer load after game discovery. An alternative explicit route such as `/play/duel/<code>` and `/play/haftgane/<code>` makes direct imports easier, but requires legacy routing, canonical link generation and game-lock updates. A new read-only lookup can avoid joining before dispatch, but adds an endpoint and separate lifecycle/error handling. The stored game remains authoritative under either route design.
5. Generate separate `duel` and `haftgane` view/catalog/fixture modules, with a small shared wire-envelope module containing only type imports. Keep overlapping names scoped by game. Retain exhaustive generated ids and per-game catalog-hash comparison. Separate instance ids from catalog definition ids where duplicate cards exist. `tygo.yaml` must map every cross-package outgoing type; contract fixtures must verify each union branch.
6. Make root shell imports independent of game catalogs, card renderers, hint tables, sound event planners and rules bodies. Lazy loading a route is insufficient if `t()` eagerly imports both games or TooltipStack imports both card components. Load game messages/renderers from the selected module while retaining a typed shared translation core and a ready state during loading.
7. Decide precache policy explicitly. Existing all-build precache can coexist with lazy execution, but it downloads both games at install. To promise on-demand downloads, change the service worker to a selected-shell precache plus cache-on-use immutable chunks and test offline navigation/update behavior. Keep both games' assets content-hashed and bounded runtime art/sound caches; never prefetch based on hidden hand contents.
8. The brief's approximately 140-KB initial JS is a supplied baseline, not a measurement from this audit. The actual cold-Home gate is 200,000 gzip bytes (`e2e/ux/budgets.spec.ts:35`), leaving about 60 KB if the same units and baseline hold. Do not spend that headroom on another full catalog. Keep the existing gate, add cold Duel entry and cold Haftgane entry budgets with service workers blocked, record shared-versus-game chunk imports, and separately measure worker install/download bytes with the worker enabled. No tested current size is claimed here.

Tradeoff: sharing low-level infrastructure reduces duplicated bug fixes and preserves one deployment. Sharing game DTOs or board components creates optional-field complexity and risks exposing hands. The useful boundary is a small typed host plus separate rules and presentation modules, with compatibility adapters for Duel rather than a wholesale rename/move of its files.
